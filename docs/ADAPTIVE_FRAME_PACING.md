# 运行时自适应视频选帧

## 1. 目标与明确撤回的判断

主目标是在正常供帧和显示容量允许时，提高 `P/A`，同时保持可达到的不同视频帧提交速率和稳定提交间隔。
P 是首次成功提交的不同视频帧数；A 是本会话、同一 video epoch 成功发布到 mailbox 的视频帧数。
重复绘制不增加 P，覆盖丢掉的帧仍属于 A。不得通过只计算 take 到的帧、减少解码或延长积压来提高比例。
这里的 present 是成功的绘制提交，不是物理 scanout。

帧龄是防止通过增加延迟换比例的约束，也是同等 P/A 时的优化项；它不是取代 P/A 的主目标。
GPU available fence 等待时长不是目标函数，不要求它缩短、不改变它的正确性语义，不移除等待。

撤回旧判断：“GPU 残余等待接近整周期，因此自适应没有达到目标”；等待不变不是相位适配失败的证据。
也撤回据此提出的“必须先关联具体输出 fence 并重构其管理”的必要性判断。
旧 `frame_pacer.c` 仅根据 fence 观测和提交余量调整提前量，没有输入帧发布反馈，也没有 P/A 反馈，
不是本方案要求的控制器，不能通过调整其固定参数冒充本方案实现。

源码依据：`video_pipeline.c` 的 publish 在 mailbox 锁内接受输出、替换 pending；
`media.c:stream_media_present` 在 `sl_gfx_begin` 成功后 take，提交成功后才能确定新帧的呈现结果；
`switch/gfx.c` 的 acquire 可能阻塞，提交后的 GPU wait 保证输出可写。调度必须观察真正的 take 时刻，
不能把 begin 前的计划时间当成已经完成的选帧时间。

## 2. 运行时学习与实际串流验证

生产控制器在每次会话/epoch 启动时，用本机实时事件学习输入周期、输入相位、提交容量、CPU 调度误差。
不保存某台机器或某段测试视频的相位、周期、提前量作为产品参数。host 回归测试与产品共享控制器实现。
真机验收使用实际串流客户端；稳定离线输入不能替代实际到帧与系统调度条件，不保留独立 pacing probe 入口。

控制器允许有通用的窗口长度、置信度阈值、无量纲步长和内存容量上限。这些是算法设计参数，
不是从离线视频搬来的运行时相位。所有时间预算由在线测得的周期、波动和工作耗时导出。
不把 16,667 us、6 ms 或特定范围的 fence 等待作为启动前提。

## 3. 产品必需的观测

在已有 mailbox 锁内发布小型元数据，不增加帧引用，不新增热路径日志或为每帧分配内存。
所有 CPU 时间使用同一个 CLOCK_MONOTONIC 时间域。

| 事件 | 数据 | 用途 |
|---|---|---|
| publish | epoch、单调 publish_seq、发布时间 | A、输入周期/相位、波动；被覆盖的发布也不能漏计 |
| take | 实际时间、所取 publish_seq、当时最新 seq | 测量真实采样相位及空取/跨多次发布 |
| submit | 批次、选中 seq、调用前时间、成功标志 | P、记录/提交耗时；失败不计 P |
| begin（仅诊断） | 尝试时间、返回时间、结果 | 区分无批次、CPU acquire 阻塞，不作为调度反馈 |
| collect（仅诊断） | 已有完成 fence 的观测、批次 | 观察完成节奏和积压；不作为调度反馈或增加外部 fence 轮询 |

使用固定容量的发布元数据 ring，例如 128 条；它不保存视频帧，不是播放 FIFO。
主线程增量读取新记录；若溢出，累计 A 仍准确，该段的相位细节标为不可用并重新学习。
发布线程只写元数据，周期估计、分位数和控制决策由主线程在新事件/控制窗口到来时更新。

P/A 按发布序号的 cohort 结算，不能直接拿任意时间窗中 P 的增量除以 A 的增量。
被 take 但尚未完成 submit 的候选不能因新 publish 覆盖就提前判丢；等该候选成功/失败后结算。
窗口尾部尚在 pending/recording 的帧延后结算。停止测试时单独处理尾部，禁止跨 epoch 混算。
submit 在 CPU 返回时确认成功，但其开始时间另记，不能把阻塞返回当成提交开始。

## 4. 在线学习两个节奏

### 输入节奏

从全部 accepted publish 时间估算 Tv 和相位 Pv，而不是只从成功 take 的样本反推。
使用跨四帧的时间差估计周期，在短窗口内取中位数并平滑；将各发布时间投影至同一序号，
以投影中位数估计相位、高分位残差估计不确定度。交替短/长间隔不等于帧率交替改变。
成批发布和长时间缺帧单独处理；短时异常保留周期，不以间隔极差超阈值关闭调度。
保护余量 gv 来自相位残差及已经观察到的“提前重复绘制后新帧到达”时间，且受 UI 服务上界限制。
整轮主循环间隔包含 acquire 阻塞，不能当作线程唤醒误差。

### 显示可提交节奏

启动学习期间保持原正常绘制，利用成功提交和已有批次完成的节奏估算 Ts 与可达到的吞吐。
这个估计是调度可行域，不是 fence 应当达到的数值。BUSY/acquire 阻塞对容量的影响由实际提交间隔体现；额外资源采样只用于诊断。
锁定输入相位不依赖外部 fence 的窄观测区间；因此不能在 interval 1 下因该观测缺失永久停留在原路径。
不以主动降速后的成功提交间隔反推显示能力下降，保留未限速基线，并在持续受限时重新测量。
GPU/显示反馈很抖或容量估计失效时恢复保守调度，仍正常处理新帧和 UI。

当输入快于显示容量，P/A 的物理上限约为 min(1, Tv/Ts)，不追求不可能的 100%。
同时报告 A/s、P/s、P/A 和正常提交间隔；30 fps 输入在 60 Hz 输出上不以重复绘制充当 60 个新帧。

## 5. 调度与控制律

控制变量是本地选帧的目标相位 θ（相对于输入发布节奏）及动态保护余量，不是 fence、解码时机或视频 FIFO 深度。

初始目标是“预期新帧发布后，留出覆盖预测/调度误差的余量取帧”。同速情况下，理想取帧落在
`publish(k)+gv` 到 `publish(k+1)-gv` 的可行区间内；区间宽度不足说明不能承诺无损采样。
目标映射到显示容量允许的提交机会；速率不同时跟踪相位漂移，不强行一对一锁死两种周期。

begin 准入采用事件优先的有界等待，不从目标时间扣除上一次 acquire 耗时。
acquire 等待来自显示资源与调用时机，改变调用相位也会改变这个耗时；它不是固定可提前量。
实际 take/submit 仍用于结果结算，不能用计划时间代替真实事件。

每轮事件处理：

1. 先处理输入、生命周期与 collect，再读取发布元数据、更新预测。
2. 到达调度门限前返回主循环；尚未 acquire，也未取出视频帧。
3. 若预测的新帧已实际发布，可在容量和节奏约束内提前准入；不为等待预测而错过已经存在的合适新帧。
4. 到门限时尝试 begin。BUSY 不消费 pending，不推进“已成功提交”的周期索引。
5. begin 成功后立即 take latest、绘制、提交，并反馈实际时刻与 seq；无新帧时仍可重绘 current/UI。
6. 下一次目标基于绝对时间与最新预测推导，避免 `本次实际返回 + 周期` 逐帧累积漂移。
   超时立即处理当前机会，不用连续补提交追赶，也不把过期门限直接顺延一个周期后继续等。

### 自适应反馈

有实际 pending 时立即尝试 begin；没有 pending 时才等待预测发布时刻，并保留正常 UI 服务上界。
一次没有 pending 的等待过程固定一个截止时间；BUSY 保持该截止时间，不能每轮向后延长。
新帧到达直接解除等待，预测过期就尝试当前机会，不排队补交旧周期。

P/A 低本身没有提供修正方向。旧的“跨多个 seq 就当成取晚了”“前后窗口比例变好就沿该方向走”
混淆了输入变化、资源压力和控制效果，不再作为控制律。
只有实际观察到重复绘制后一个输出周期内到达新帧，并且结算 cohort 存在损失时，才扩大有界覆盖余量。
接近可达到的 P/A 上限时缓慢回收额外余量，不进行盲目的左右相位搜索。
丢失元数据或短时断供保留输出容量；真正暂停/时间倒退才重新初始化两种时钟。

输出容量优先由未主动等待的连续提交估算。若持续等待导致这类样本不足，连续四次显著更慢或更快
的提交间隔允许重测容量，避免算法永远冻结在旧显示速率。两缓冲启动时的一两次突发不构成容量变化证据。

## 6. 启动、恢复与可实现性

冷启动先以原路径输出，同时用约 8–16 个输入事件建立粗估计；随后的短控制窗口修正相位。
稳定、约 60 fps 且存在足够可行窗口时，验收目标是启动/恢复后 1–2 秒进入高 P/A 的稳定区间。
这是一项必须在随机初相位下验证的要求，不是从周期稳定就能数学保证的结论。
低帧率时事件数不足需单独定义收敛预算，不能伪报同等置信度。

慢速时钟漂移持续跟踪；短暂缺帧不抹掉整套估计；持续异常、epoch 变化、长期暂停或容量改变重新学习。
解码不受调度门影响，始终尽快处理输入。没有新帧不无限等待，保留 UI/退出的服务节奏。
算法必须区分“学习中”“稳定”“受容量限制”“输入/调度不稳定”，而不是把所有情况都叫锁定。

同速稳态仍可能没有足够宽的可行取帧窗口，例如 CPU 被长时间阻塞。这时仅调整相位不能保证接近满利用率；
需要把限制暴露为可行性失败，不能靠缩小 A、积压视频或修改 fence 定义让统计好看。

## 7. 工程边界与 release

- `video_pipeline`：增加产品必需的 publish_seq 和小型发布元数据快照；生命周期与 latest mailbox 不变。
- `media`：在 begin 前请求调度，在真实 take/submit 后反馈，并按 cohort 结算 P/A。
- 独立 controller：只处理元数据和单调时间，不接触 AVFrame、GPU 引用、协议状态或 SDK fence。
- `gfx`：保持 acquire→GPU wait→绘制→完成 fence→present 的正确性链；提供结果和必要时间反馈。
- 不新增后台线程、解码帧队列或跨主循环持有的新 acquired 输出；stop→join→destroy 顺序保持。

产品控制器的元数据与低频估计不能放进 `NSL_DIAGNOSTICS`，否则 release 将失去自适应能力。
诊断宏控制额外日志、图表采样、GPU reports、CPU 占用统计和基线比较入口；诊断 OFF 是默认。
纯诊断累计计数与就绪/等待时间字段也由宏排除，release 不分配这些字段、不更新这些计数。
控制所需的 publication ring、cohort 窗口、周期/相位估计始终保留；不保留旧升频实验和 begin 耗时反馈接口。
不允许诊断开关改变控制律、观测来源或学习参数。实验比较开关与产品算法启用开关分开。

Deko release 链接 `deko3d`，诊断版链接 `deko3dd`，使用独立查找缓存。
`python3 scripts/check-release-diagnostics.py <build目录>` 检查主要对象的诊断宏、日志字符串、GPU report
符号和正式库链接；必要的引用计数、完成 fence 与协议时间戳不删。

## 8. 自审与算法验收

| 审查问题 | 约束/验收 |
|---|---|
| 算法只根据自己设置的 target 宣布成功 | 必须看真实 publish、take、成功 submit 和 P/A |
| 分母遗漏被覆盖帧，或窗口边界把 P/A 算错 | accepted publish 全计数；cohort 尾部延后结算 |
| 用减少解码/降低吞吐伪造比例 | 同时比较 A/s、P/s、容量上限和稳态间隔 |
| 以 fence 等待减少作为成功标准 | 明确排除；等待保持不变允许算法成功 |
| 没有精确 fence 时间就不学习 | 输入 publish 和实际提交事件为主要信号，不依赖额外外部 fence 轮询 |
| acquire 阻塞改变了计划相位 | 以实际 take 时间反馈，不把计划时间当事实 |
| 网络缺帧与采样过早混淆 | 利用 publish 历史区分；缺帧不盲目移动相位 |
| 通过增加在途队列或保留视频换比例 | 无新增帧队列；帧龄和积压为硬约束 |
| 不同运行的初相位被当作算法收益 | 实际客户端记录输入条件与控制器状态，不凭两次运行均值差宣称因果收益 |
| release 的算法没有诊断数据就失效 | diagnostics ON/OFF 的同事件回放须产生相同调度决策 |
| 一两秒之后仍只说“学习中” | 稳态随机相位冷启动测试统计收敛时间、失败率，未达标即失败 |

host 确定性模拟覆盖：全部初相位、输入/输出近似同速但慢漂移、30/60/不同速率、少量调度抖动、
短时断供、批量发布、恢复和 acquire 延迟。控制器必须与机器运行时使用同一份代码。
使用无调度基线及已知可行区间的理想采样器作对照，报告收敛时间、P/A、P/s、长间隔与帧龄。

真机使用实际串流客户端，不输出产品标定参数；比较时同时核对输入速率、抖动和控制器工作状态。
对于稳定且 Av≈60/s、显示容量≈60/s 的受控输入，可将收敛后 P/A≥98%、P/s 不劣于基线及无持续额外积压
作为首轮明确验收线；阈值是测试要求，不是控制器运行时偷看的答案。不能以单次好结果代替不同初相位验证。
对不满足可行性前提的场景报告限制，不承诺无条件 100%。

## 9. 阻塞渲染路径的机制审查

实际串流证据：`build/switch-deko/interactive-runs/publication-pacing/session.log` 中约 119 秒
有供帧区间 P/A 约 91.4%，CPU acquire 平均约 13.9 ms。秒级采样只有 12/118 次满足旧 active 条件。
该采样比例不是精确时间占比，也不能独立定位每次退出预测的原因。

撤回以下机制假设，而不仅是修改阈值：

1. 相邻发布间隔极差必须小于周期 25% 才能调度。交替到帧可以保持稳定长期帧率，却持续违反该条件。
2. 上次 acquire 耗时是可从下次等待里扣除的准备时间。这种相位相关阻塞可接近整个周期，扣除后会
   把调用重新推到新帧之前；即使 active 一直为真也可能无收益。
3. 原 host 测试只模拟输出槽未到时返回 BUSY、到时立即成功，没有模拟 CPU 在 acquire 内阻塞而
   解码继续发布。它不足以验证真实路径中的控制效果。

`frame_pacer` 使用发布序号/时间、实际提交和 cohort 结果；`video_scheduler` 负责 pipeline 同步。
产品与测试共享实现。gfx 不包含控制器，不增加外部 fence 观测，不改变 fence 的等待或生命周期。

输入估计使用最近最多 16 次发布的跨四帧斜率和投影中位数，输出估计使用 16 项有效间隔；
不保留相邻间隔极差硬开关、整轮循环唤醒误差、acquire 成本补偿或无方向依据的比例爬山参数。

无 pending 时的候选截止时间：

- 输入相位 + 在线输入周期 + 有界保护余量；
- 上次提交 + 在线输出周期 + 有界 UI 余量。

取两者较早者并固定至本次尝试提交结束。保护余量最多半个输出周期；输入明显慢于输出时不额外
延后 UI 服务。新的真实 pending 始终优先。截止过期不滚动延长，BUSY 不推进成功提交时钟。
输入短暂中断只重置局部拟合窗口/相位锚点，不抹掉已学周期和输出能力。

诊断 `vq9` 记录允许预测的累计时间、实际主动等待时间、从首次发布到首次具备预测条件的时间，
以及输入时钟保持次数。首次具备条件不是 P/A 已经收敛的证明；P/A 仍由 `vq8` 的 cohort 核对。
这些诊断字段不参与调度，diagnostics OFF 不更新它们。

`NSL_ADAPTIVE_PACING=ON` 在 deko 客户端启用产品调度，独立于 `NSL_DIAGNOSTICS`。
诊断版 `--no-adaptive-pacing` 用于真实串流基线比较。
验证面向实际客户端；host 模型增加“acquire 阻塞期间输入持续发布”、到帧交替偏移、保持与恢复、
截止时间不滚动、持续主动调度时的双向输出容量变化，以及 diagnostics ON/OFF 决策一致性。
模拟不能重放当前日志中没有记录的逐帧事件，更不能用模拟的 100% 宣称真实串流也达到 100%。
